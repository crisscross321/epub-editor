# 素笺接入 LLM 的设计方案

日期：2026-08-31
基线：`bd0d0ac`
前置：`PRODUCT-REVIEW-2026-08-31.md`（功能审查）

---

## 零、先回答一个前置问题：该不该做

素笺现在的承诺是「本地编辑，导出带走，没有账号，没有云」。接入 LLM 会打破其中一条。所以先明确：

**不该做的理由（先摆出来）**

- 定位冲突。用户选素笺很可能正是因为它不联网、不上传
- 中文写作类 AI 功能同质化严重，做不出差异
- 引入 Key 管理、计费、失败重试、超时，复杂度陡增
- 手机端上下文窗口有限，长篇小说的"全书理解"做不到，容易做成玩具

**该做的理由**

- 素笺的核心场景是「改书」和「写长篇」，这两件事里有大量**机械但需要判断力**的脏活，规则做不了、人做很累。这正是 LLM 的甜区。
- 用户自带 Key 的模式可以完全绕开账号和计费问题。
- 更重要的：素笺已经有一层被低估的资产 —— **它是唯一能同时看到「全书结构 + 每章正文 + 阅读进度 + 笔记划线」的地方**。这个上下文是通用 AI 助手拿不到的。

**结论：做，但必须遵守三条红线**（下一节）。

---

## 一、三条红线

这三条是整个设计的地基，任何功能都不能违反。

### 红线一：LLM 永远不直接写入正文

所有模型输出都进入「建议层」，变成待确认的 diff。用户逐条采纳或整体拒绝。采纳后才写入，并同时进版本快照。

**为什么**：写作者对自己的文字有主权。AI 静默改字是最快失去信任的方式。而且素笺的用户往往是在改**别人的书**或写**自己的长篇**，两种场景都容不得意外改动。

### 红线二：LLM 是可选增强，不是运行依赖

不填 Key、没网、模型挂了、余额用尽 —— 素笺的全部现有功能必须照常工作。所有 AI 入口在不可用时应当隐藏或明确置灰，不能报错阻断。

**为什么**：这决定了素笺是"一个能用的工具，附带 AI"还是"一个没网就废的 AI 应用"。

### 红线三：数据出境必须用户逐次可知

明确告知发送范围，绝不默认全书上传。

- 章节级操作 → 只发这一章
- 选中文本操作 → 只发选中部分 + 少量上下文
- 需要全书上下文的功能（如全书一致性检查）→ 单独确认，且默认关闭

设置里提供「本次会话已发送 N 章 / 约 M 字」的可见计数。

## 二、能力分四层，不要一步到云

| 层 | 能力 | 依赖 | 默认 |
|---|---|---|---|
| **L0 本地规则** | 全半角、多余空行、省略号、引号规范、行首空格 | 无 | 开启 |
| **L1 端侧小模型** | 的地得、著着、病句、重复用词、错别字 | 可选下载模型 | 关闭 |
| **L2 云端模型** | 润色、改写、续写、摘要、章节命名、一致性检查 | 用户 Key + 网络 | 关闭 |
| **建议层** | 把 L1/L2 输出变成可确认的 diff | 无 | 常驻 |

**关键判断：L0 必须先做，且不要等 LLM。**

功能审查里的「一键整理文稿」（全半角、空行、省略号）纯正则就能做完，不需要模型。这部分能覆盖用户 80% 的实际痛点，成本几乎为零。**先把 L0 做扎实，再考虑上面几层** —— 否则会出现"用大炮打蚊子还打不准"的尴尬：让 LLM 去改全角半角，又慢又贵，还可能改错。

L1 是个观察项。端侧中文纠错模型（几十 MB 量级）在 WebView 里跑 ONNX 是可行的，但收益要实测。如果 L0 已经解决大部分问题，L1 可以直接跳过。

## 三、具体功能设计（按价值排序）

### 3.1 校对助手 —— 最该做的一个

**场景**：写完一章，或者刚导入一本网上下载的书，想知道哪里有问题。

**输入**：单章正文
**输出**：问题列表，每条含位置、类型、原文、建议、理由

分类：
- 错别字 / 别字（的地得、著着、其它其他）
- 病句、语序不通
- 重复用词（同一段落里反复用同一个词）
- 前后不一致（人名、地名、称呼在本章内出现两种写法）
- 标点误用

**交互**：列表形式，每条可「采纳」「忽略」「全部同类采纳」。不做自动应用。

**为什么这个最该做**：
1. 它和素笺的核心场景（改书、写长篇）完全对齐
2. 输出是**离散的、可逐条验证的**，不是大段改写 —— 用户容易判断对错，信任建立快
3. 它是唯一在"改别人的书"这个入口下也成立的 AI 功能

**技术要点**：必须返回结构化结果（JSON），带原文片段用于定位。不要让模型返回整章改写稿 —— 那样无法做 diff，用户也无法逐条判断。

### 3.2 章节命名与摘要

**场景**：导入一个 txt 分了 40 章，全都叫「未命名」。或者写完一章懒得起名。

**输入**：单章正文（可截断到前 N 字）
**输出**：3 个候选章节名 + 一句话摘要

这个功能价值密度很高：
- 输出短，成本低，速度快
- 结果好坏一眼就能判断
- 直接接在现有的「导入分章预览」流程后面，顺理成章
- 摘要可以写进 `dc:description` 或章节备注

**批量场景**：导入后一次性为所有空标题章节生成候选名，用户在预览列表里挨个确认。这个体验会很爽。

### 3.3 全书一致性检查

**场景**：长篇写到 50 章，忘了配角姓什么、某个地名前后写法不一致、人物年龄前后矛盾。

**输入**：全书（分批发送）或人物设定卡 + 抽样章节
**输出**：不一致清单

这是**素笺相对通用 AI 助手最有优势的功能** —— 因为只有素笺同时握着全书结构和每章正文。ChatGPT 里做这件事要手动贴 50 章。

但它也是最贵最慢的：
- 必须分批调用，成本明确告知
- 默认关闭，单独确认数据出境
- 建议做成"后台任务"形态：点一次，等一会儿，回来看报告
- 结合功能审查里的「人物设定卡」使用效果最好 —— 设定卡作为 ground truth，检查正文是否偏离

### 3.4 选区改写

**场景**：选中一段，觉得写得啰嗦。

**操作**：选中文本 → 呼出菜单 → 精简 / 扩写 / 换语气 / 改书面语

**输出**：并排显示原文与改写，用户决定是否替换。提供「再来一版」。

这是最常见的 AI 写作功能，也是最容易做成"鸡肋"的 —— 因为它侵入创作过程最深。建议：
- 只在用户主动选中文本后出现，绝不主动弹
- 默认不做「续写」（见第五节）

### 3.5 阅读侧：问这本书

**场景**：读到一半，想问「前面那个姓陈的是谁」。

用现有的全书文本 + 检索，把相关段落喂给模型回答。

这个优先级低 —— 按功能审查的判断，阅读器是配角。但它有个副产品价值：**同一套检索基础设施可以复用给 3.3 的一致性检查**。如果要做 3.3，这个几乎是白送的。

## 四、技术方案

### 4.1 Key 与供应商

**用户自带 Key（BYOK）**，不做代理服务。

理由：素笺没有后端，加代理就等于加运维、加成本、加账号体系，与定位彻底冲突。

配置项：
- 供应商预设（OpenAI 兼容接口为主，覆盖大部分国内外服务）
- Base URL 可改（支持自建 / 中转 / 各家兼容端点）
- 模型名可填
- Key 存在本地（`localStorage` 或 IDB），明确告知不上传

**注意**：项目当前零网络代码（全库搜 `fetch(` 无结果），但 `AndroidManifest.xml` 里 `INTERNET` 权限已存在。所以加网络能力不需要动原生层，但需要新增网络安全配置以限制可访问域名。

### 4.2 挂载点

现有代码里有几个天然的挂载位置：

| 功能 | 挂载点 |
|---|---|
| 校对助手 | `EditorToolbar` 新增按钮，结果面板复用 `FindReplaceBar` 那一层的位置 |
| 章节命名 | 导入分章预览流程 + `ChapterListScreen` 章节行 |
| 选区改写 | `PreviewScreen` 的 `sel-pop` 已有选区浮层，编辑器侧需新增 |
| 建议层 diff | 新增组件，但可复用 `epub/replace.ts` 的文本节点遍历做定位与应用 |

`epub/replace.ts` 的 `replaceAllInDoc` 已经是「在 doc 树上按文本替换并计数」，建议层应用 diff 时可以直接复用这个模式。

### 4.3 建议层的数据结构

```
Suggestion {
  id
  chapterId
  kind: 'typo' | 'grammar' | 'repeat' | 'consistency' | 'punctuation' | 'rewrite'
  anchor: 原文片段（用于定位，不用字符 offset）
  before / after
  reason
  status: 'pending' | 'accepted' | 'ignored'
}
```

**用原文片段而非字符偏移做定位**。因为用户可能在等待模型返回的过程中继续编辑，offset 会失效。应用时先在当前文档里找 anchor，找不到就标记「原文已变化，无法应用」。

建议存进 IDB（新增一个 store），这样：
- 关掉面板再打开还在
- 「忽略」过的建议不再重复提示
- 可以统计采纳率，反过来调整 prompt

### 4.4 失败与降级

必须显式处理：网络失败、超时、Key 无效、余额不足、返回格式不合法、内容被安全策略拦截。

每种都要有中文提示，且**不影响正在进行的编辑**。参考现有 `epub/errors.ts` 的 `EpubError` 模式，加一组 `LlmError`。

长文本必须分块，且要让用户看到进度（"正在检查第 3 / 12 段"）。

## 五、明确不做

| 不做 | 理由 |
|---|---|
| **AI 全自动续写整章** | 素笺是写作工具不是生成器。续写会让作品所有权变得模糊，也会让"我在写作"变成"我在审稿"。如果用户想要，市面上一堆专门产品 |
| **AI 直接改正文（无确认）** | 违反红线一 |
| **默认上传全书** | 违反红线三 |
| **官方代理 / 内置额度 / 会员** | 需要后端、账号、计费，与本地优先定位彻底冲突 |
| **AI 生成封面图** | 与核心场景无关，且图片生成成本和合规问题都更复杂 |
| **对话式写作助手（聊天框）** | 手机屏幕小，聊天框会挤占正文空间。素笺的 AI 应该是「贴在文字旁边的建议」，不是「另一个说话的人」 |

最后一条值得多说一句：很多产品加 AI 的方式是塞一个聊天侧边栏。在手机上这是错的 —— 屏幕就那么大，正文和对话抢空间。素笺的 AI 形态应该是**无形的**：在需要的地方出现一个建议，用完就消失。

## 六、落地顺序

**第一步（不含 LLM）**
1. L0 本地规则整理文稿
2. 章节级版本快照

第 2 项是第一步的前提 —— **没有版本回溯就不该让 AI 碰正文**。这两项本身也在功能审查的优先级里，属于该做的事。

**第二步（最小可用 LLM）**

3. Key 配置 + 网络层 + `LlmError` 降级
4. 章节命名与摘要（最小闭环，输出短、易验证、成本低）

选它做第一个 AI 功能，是因为它风险最小 —— 猜错了章节名没有任何损失，用户重点一下就好。用它把网络层、错误处理、建议层的基础设施跑通。

**第三步（核心价值）**

5. 建议层 + 校对助手

这是整个 LLM 方案里价值最高的一块。

**第四步（差异化）**

6. 选区改写
7. 人物设定卡（先做非 AI 版本）
8. 全书一致性检查（依赖 6、7 和检索基础设施）

第 8 项是素笺相对通用 AI 助手最有优势的功能，但它也最重，放在最后。

---

## 七、一句话总结

**LLM 在素笺里应该是校对员，不是代笔。**

它的位置是「在你写完之后指出问题」，而不是「替你写」。这个定位一旦守住，前面所有设计决策（建议层、不做续写、不做聊天框、BYOK）都是自然推论。
