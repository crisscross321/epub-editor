# 素笺功能审查清单

日期：2026-08-31
基线：`bd0d0ac`（30 个测试文件 / 117 个用例全绿）
审查目标：作为「好用的移动端 EPUB 工具」，功能层面还缺什么、哪里是错的

---

## 结论先行

当前版本的 EPUB 引擎（解析、按章简化、未编辑章节字节级回写、打包）是这个项目最扎实的部分，测试也覆盖得不错。问题集中在三处：

1. **数据可能真的会丢。** 全部书稿只在 IndexedDB，既没申请持久化配额，也没有任何「切后台 / 进程被杀」时的落盘钩子。最坏情况是用户敲完一段、切到微信、系统回收 WebView，那 800 毫秒防抖窗口里的内容直接没了。
2. **移动端最关键的入口没接。** 无法从文件管理器、微信、QQ 里「用素笺打开」一个 epub。一个手机 EPUB 工具却只能从应用内文件选择器进入，等于自断一半使用场景。
3. **有几个功能是「看起来有、实际没有」。** 划线保存了但正文里不显示；书籍信息页让用户填了出版社/系列/标签，导出时全部丢弃；导出不生成 toc.ncx，老阅读器打开看不到目录。

下面按优先级列具体项。

---

## P0 · 数据不能丢（做这个之前别做别的）

### 1. 申请持久化存储配额

现状：全库搜索 `navigator.storage.persist` 无任何调用。

IndexedDB 默认是 best-effort。Android 存储紧张时，WebView 的站点数据是系统优先回收对象。启动时应调用 `navigator.storage.persist()`，并把结果告诉用户 —— 拒绝了就要更强提示导出。

### 2. 补齐生命周期落盘

现状：`App.tsx` 里 `onDocChange` 用 800 毫秒防抖写库（`saveTimer`），只有 `leaveEditor` 会主动 flush。全库搜索 `visibilitychange` / `pagehide` / `appStateChange` 均为零结果。

需要：`document.visibilitychange`（hidden 时立即 flush）+ Capacitor `App.addListener('appStateChange')`（isActive 变 false 时 flush）。另外防抖 800 毫秒对手机偏长，建议缩到 400 毫秒，或改成「字数变化超过阈值就立即写」。

### 3. 回收站会永久残留

现状：`App.tsx` L543 删书后 `setTimeout(purgeTrash, 10_000)`。10 秒内杀进程，`trash` store 里的完整快照（含全部 entries + blobs）就永远留在 IDB 里。

`snapshotBook` 是全量拷贝，删一本 30MB 的图文书就多占 30MB，用户完全不知情。需要：启动时扫描 `trash`，清掉超过阈值（如 7 天）的记录；设置页显示回收站占用并给手动清空入口。

### 4. 没有容量预检

导入大 EPUB / 插图前应查 `navigator.storage.estimate()`，空间不足时提前拦住并说明，而不是写到一半抛异常。

### 5. 备份路径太窄

现状：`saveBytesToUser` 在 Android 上写 Cache 目录再拉 Share 面板，用户取消就什么都没留下（代码里也只能返回「请再点一次导出」）。

需要至少一条不依赖用户在面板里正确操作的路径：
- 直写公共 Downloads（SAF 或 `Directory.ExternalStorage`）
- 书架支持「全部导出」批量备份
- 可选：每天首次打开时自动把改动过的书导出一份到应用外目录

### 6. Blob URL 从不释放

现状：`bookService.blobUrlFor` / `coverUrl` / `hydrateDocImages` 全部 `URL.createObjectURL`，全库只有 `storage/files.ts` L91 一处 revoke。

`refreshShelf` 每次都为所有书重建封面 URL，进出章节每次都重建插图 URL。长会话内存单调增长，图文书尤其明显。需要按书缓存 URL，或在 effect cleanup 里 revoke。

## P1 · 移动端入口与编辑手感

### 7. 接系统「用素笺打开」

现状：`AndroidManifest.xml` 只有 LAUNCHER 一个 intent-filter，搜 `ACTION_VIEW` / `ACTION_SEND` 均无结果。

补 `ACTION_VIEW`（`application/epub+zip`、`.epub` 后缀、content/file scheme）和 `ACTION_SEND`，配合插件读入 URI。这是手机工具与桌面工具最本质的差别，优先级应高于任何编辑器细节。

### 8. 输入时的全量重解析

现状：`SimpleEditor.emitChange`（L93）每次 `onInput` 都执行 `simplifyXhtml('<div>' + 整章 innerHTML + '</div>')`，把整章 DOM 解析成 JSON。同时 L172 `wordCount={countChars(textFromDoc(currentDoc()))}` 在**每次 render** 又跑一遍完整 `currentDoc()`。

一章几万字时，每敲一个字要做两次全章解析。手机上会明显掉帧。方案：字数改成防抖计算并缓存；`emitChange` 与保存共用一次解析结果，不重复调 `currentDoc()`。

### 9. 替换后无法撤销

现状：撤销/重做走 `document.execCommand('undo')`，依赖浏览器原生 undo 栈。但「全章替换」分支（L216-219）直接 `el.innerHTML = toInnerHtml(doc)` 重写 DOM —— 这会清空原生 undo 栈。

结果：用户点了「全部替换」发现改错了，撤销按钮无效。要么自己维护快照栈，要么替换后提供一次性「撤销此次替换」入口。

### 10. 打 H1 会被瞬间拆章

现状：`onDocChange`（L321-337）检测到 `splitDocByH1` 结果多于一段就 `willSplit ? 0 : 800` —— 零延迟拆章并跳转路由。

写作中途打出一个一级标题，屏幕会立刻跳到一个新章节。这个行为很惊悚，且不可撤销。建议改成：拆章前弹确认，或者只在离开编辑器时结算，或者给一次撤销机会。

### 11. 没有粘贴处理

全库搜 `onPaste` 无结果。从微信/浏览器粘贴富文本，DOM 里会先塞进一堆 span 和内联样式。虽然 `simplifyXhtml` 最终会清掉块级结构，但过程不可控。应显式接 paste 事件，只取纯文本 + 基础格式。

### 12. 缺中文写作的基本排版

`spec` 里把段首缩进列为「不做」，但作为中文写作工具这是硬伤 —— 全库搜 `text-indent` 无结果，导出的 EPUB 段落全部顶格。建议至少支持：

- 段首缩进（两字符，可开关，写进导出 CSS）
- 场景分隔符（`***` / 居中三点）
- 引用块

### 13. 章内切章

现状：编辑一章后必须返回章节列表才能进下一章（`goBack` 还会弹「离开编辑？」确认）。写长篇时这条路径要点 3 次。编辑器底部应有「上一章 / 下一章」。

### 14. 键盘遮挡是手写补偿

`keepFocusVisible.ts` 有 150 行手写逻辑，`keyboardPadding` 里还有 `innerHeight * 0.45` 的猜测兜底 —— 这个魔数本身就说明该路径不可靠。建议真机复测，优先用 `VirtualKeyboard API` + `interactive-widget=resizes-content` 替代猜测。

### 15. 章节重排只能一格一格点

现状：`onMove(id, ±1)` 或 `onMoveTo`（走 `window.prompt`）。100 章的书要把末章移到开头得点 99 次。需要长按拖拽排序。

### 16. 两处原生 prompt

`App.tsx` L637（移到第几章）、`PreviewScreen.tsx` L513（写笔记）都用 `window.prompt`。Android WebView 里样式突兀，与纸墨风格完全割裂，且笔记只能单行输入。改成应用内 Dialog。

## P2 · 成书质量（导出的书能不能拿出去）

### 17. 不生成 toc.ncx

现状：`packEpub` 只写 EPUB 3 的 `nav.xhtml`。全库搜 `toc.ncx` 只在 `fixtures.ts` 出现（测试夹具里有，导出里没有）。

不少国产阅读器和 Kindle 转换链路仍依赖 NCX，打开会显示「无目录」。EPUB 3 允许同时带 NCX 向下兼容，成本很低，收益直接。

### 18. 元数据填了但不导出

现状：`BookInfoScreen` 让用户填 description / publisher / series / tags，`BookRecord` 也存了。但 `packEpub` 的 OPF metadata 只写 identifier / title / creator / language / modified / cover —— 全库搜 `dc:description`、`dc:publisher`、`belongs-to-collection` 均无结果。

用户白填。需要补 `dc:description`、`dc:publisher`、`dc:subject`（tags）、`belongs-to-collection`（series）。同时 `parse.ts` 导入时也没读这些字段，往返一次全丢。

### 19. 导出不带 CSS

现状：`docToXhtml` 生成的 head 里只有 title 和 charset，没有样式表。

所有排版交给阅读器默认值，同一本书在不同阅读器里行距/段距/标题层级差异很大。应生成一份最小 CSS（中文行距、段距、标题比例、图片宽度上限、可选段首缩进）写进包内并在 manifest 注册。

### 20. 原书插图被降质

现状：`materializeImages`（bookService L223）对 pristine 章节的图片统一走 `compressImage`，压到 1600px 长边、2MB 内。

这和「尽量保真」的产品承诺矛盾 —— 打开别人的书只是想改错字，插图却被重编码了。而且原始 entry 仍留在 IDB 里，同一张图占两份空间。建议：原图未超限就不动它；导出时优先用原始字节。

### 21. 导入分章规则太窄且不可预览

现状：`splitImportedText` 只认 markdown `#`/`##` 和 `第X章`。不认「第一节」「Chapter 1」「序」「楔子」「番外」「卷一」。

导入一个 txt 分错了，只能手动一章章切。需要：扩充预设规则 + 允许自定义分隔规则 + **导入前预览分章结果并确认**（这一条最重要，分错了当场能看出来）。

## P3 · 阅读与体验

### 22. 划线是假的

现状：`reader/style.ts` L31 定义了 `.hl` 样式，但全库再无第二处引用 —— annotation 存进了 IDB，重新打开正文里不显示任何划线痕迹，只能在笔记抽屉里看到文字。

要么按 annotation 在渲染时回填 `.hl`，要么明确降级为「摘抄」不叫划线。

### 23. 书签定位不到位置

`Annotation` 只存 `chapterId`，不存章内 offset。点「打开」只跳到章首。长章节里等于没定位。

### 24. 翻页模式会切断行

现状：`turn()` 用 `doc.scrollTop = next * doc.clientHeight` 模拟分页。这必然在页边界把一行字上下切半。真分页需要 CSS multi-column 或按行高对齐容器高度。

### 25. 全书搜索会很慢

现状：`searchBook` 串行 `await chapterPlain(每一章)`，而 `chapterPlain` 内部走 `getChapterPreview` → `hydrateDocImages(kind: 'data')` —— **把每张插图转成 base64 data URL**，只为了拿纯文本。

一本图文书搜一次要 base64 全部图片。需要单独一条只提文本的路径（跳过图片），并考虑建纯文本索引缓存。

### 26. 搜索结果只跳章不跳位置

`hits` 里带了 `index`，但 `jumpTo(next)` 把它丢了，offset 传 0。应换算成章内偏移并高亮定位。

### 27. 章节列表缺状态信息

现状：只显示章名和「尚未编辑」。看不出每章字数，无法快速找到「哪章还是空的 / 哪章太长该拆」。建议每行补字数，并支持按「空章」筛选。

### 28. 信息架构重叠

`ChapterListScreen` 顶部塞了书名/作者/摘要三个输入框 + 全书替换表单 + 章节列表；同时 `BookInfoScreen` 又完整重复了这些字段。首屏噪音大、职责不清。建议章节页只留「书名 + 封面缩略 + 进入书籍信息」，替换收进操作菜单。

### 29. 没有写作统计

写作工具缺动力机制：今日字数、本书总字数、字数目标。数据已经都在库里，成本很低。

### 30. 横屏/平板未适配

`.app` 固定 `max-width: 720px` 居中，横屏时编辑区被压得很窄。至少让横屏下编辑区用满宽度。

---

## 建议的推进顺序

| 阶段 | 内容 | 理由 |
|---|---|---|
| 第一轮 | 1、2、3、6、7 | 先堵住丢数据和内存泄漏，再把系统打开入口接上。这五项决定「能不能安心用」 |
| 第二轮 | 8、9、10、17、18 | 编辑手感的三个硬伤 + 导出的两个硬伤。做完这轮，产出的书才算能拿出去 |
| 第三轮 | 12、13、15、19、21 | 中文排版、长篇写作动线、导入准确性 |
| 第四轮 | 22–30 | 阅读侧与体验打磨 |

其中第 7 项（系统打开入口）虽然排在第一轮，但它是纯 Android 侧改动，可以和数据安全项并行做，互不冲突。
